# TMS v2 — V1 Design

A truth maintenance system built from text-based statements: a number-free epistemic ledger that agents can query for belief states, backed by observations and sources, served over MCP.

This document describes the v1 design. [db/init.sql](db/init.sql) is authoritative for the storage contract: PostgreSQL with pgvector and four tables. The evaluator and MCP behavior below are intended application contracts, not functionality supplied by SQL. Open evaluation decisions and SQL initialization issues are called out explicitly.

---

## The Discipline

1. **No confidence numbers or degrees.** No probabilities, likelihoods, weights, scores, or ordered confidence labels such as “weak / moderate / strong.” An ordered label set is still a scale; the system's currency is statements, not points on a scale.
2. **Never aggregate confidence.** Evaluation follows evidence relationships rather than weighted summation. Counts describe records and sources, not the strength or probability of a claim.
3. **Contested is an answer.** Show surviving support and objections rather than smoothing disagreement into a number. Cycle handling and its mapping to statuses still need an explicit evaluator contract (§3).
4. **Claims may contain numbers; evaluation never computes with them.** “The company laid off 15% of staff” is a legitimate claim. A confidence rating is not an input to evaluation.
5. **External layers may compute numbers from the ledger, but cannot add score fields to it.** A layer may record an output as opaque claim text, with evidence, like any other statement (§8).

---

## 0. The Base Layer: A Ledger, Not a Triple Store

The base layer is deliberately minimal. Triple stores, entity graphs, and ontologies are possible projections over it, not its underlying model.

1. **Claims are opaque text.** The base layer does not decompose a claim into subject/predicate/object, extract entities, or structure what a claim is about. Interpretation belongs to agents and optional projections.
2. **The vocabulary is fixed.** Four tables — `sources`, `observations`, `claims`, and `evidence` — with typed foreign keys and three evidence relations. There are no user-defined predicates or schema-in-data hooks.
3. **Evaluation reads relationships, not claim internals.** The intended evaluator follows evidence and provenance without interpreting the statements themselves. Precise standing rules remain to be settled (§3).

The boundary is agentic: an agent interprets text on ingestion and on retrieval. Type only what the system must itself operate on; store as text what an agent can read. A ledger record is an assertion, not a guarantee of truth.

Evidence is a row with its own identity because other evidence must be able to address whether that particular observation applies to its target. This supports objections to evidence applicability without turning the ledger into a generic ontology.

## 1. Core Idea

- The **ledger** is append-only: sources, observations, claims, and evidence.
- A **world state** is a query over claims and their derived statuses at a ledger cutoff, not a stored snapshot.
- **Statuses are derived at query time.** No status, standing flag, confidence score, or verdict is stored in the four tables.
- Statements about sources, identity, classifications, or prior verdicts can themselves be opaque claims with evidence. This does not turn those statements into typed metadata or automatic identity resolution.

## 2. Data Model (PostgreSQL)

Every table has a `text` primary key `id` and `asserted_at timestamptz NOT NULL DEFAULT now()`. The server supplies IDs. The database supplies assertion timestamps; they are not agent-supplied write arguments.

| Table | Columns beyond `id` and `asserted_at` | Meaning and constraints |
|---|---|---|
| `sources` | `name text NOT NULL`, `uri text` | Origin of an observation. `name` must be nonblank after trimming; `uri` is nullable. No trust or reliability score. |
| `observations` | `source_id text NOT NULL`, `uri text NOT NULL`, `content text`, `content_hash text NOT NULL`, `embedding vector(4096)`, `embedding_model text` | Immutable document record. `source_id` references `sources(id)`. Content is nullable in SQL, even when an API example supplies it. The hash is indexed but not unique. |
| `claims` | `text text NOT NULL`, `embedding vector(4096)`, `embedding_model text` | Opaque statement. SQL requires positive text length, not trimmed nonblank text. Claim text is not unique. |
| `evidence` | `relation text NOT NULL`, `from_observation_id text NOT NULL`, `target_kind text NOT NULL`, four nullable target IDs, `reason text NOT NULL` | An assertion that an observation bears on exactly one target, with a nonblank reason. Details below. |

For both observations and claims, `embedding` and `embedding_model` are **paired nullable**: either both are present or both are null. Evidence and sources have no embedding columns.

### Evidence foreign keys and constraints

- `from_observation_id` references `observations(id)` and is always required.
- `target_kind` is one of `claim`, `evidence`, `source`, or `observation`.
- Exactly one of `target_claim_id`, `target_evidence_id`, `target_source_id`, or `target_observation_id` is populated, matching `target_kind`. Each references the corresponding table's `id`.
- `relation` is exactly `SUPPORTS`, `REBUTS`, or `QUALIFIES`.
- `QUALIFIES` can target only a claim. SQL allows both other relations to target all four kinds.
- `reason` must be nonblank after trimming. It explains why the observation bears on the target, in specific, checkable language. “Supports weakly” is not an acceptable explanation under the discipline, although SQL checks only that a reason is nonblank.

The reason requirement belongs to **evidence**, not to every foreign key. An observation's `source_id` is its provenance link; it has no separate reason field.

### Evidence vocabulary

- `SUPPORTS`: the observation provides grounds for the target.
- `REBUTS`: the observation provides grounds against the target.
- `QUALIFIES`: the observation adds a condition or caveat to a claim.

A rebuttal can concern the claim itself, the applicability of a particular evidence record, a source, or an observation's integrity. Those are different targets, not additional stored relation types. SQL records the assertion; it does not define how each target affects derived standing (§3).

### Nothing derived is stored

`status`, `standing`, `support.chains`, `support.distinct_sources`, and `collapse_conditions` are query results only. There are no identity-link, document-dependence, or document-version tables. Repeated hashes or claim text remain valid distinct records; there is no content-hash deduplication or idempotency requirement.

## 3. Statuses and Evaluation

The intended claim-status vocabulary is:

| Status | Intended reading once standing has been defined |
|---|---|
| `unresolved` | No standing support and no standing rebuttal. |
| `believed` | Standing support and no standing rebuttal. |
| `disbelieved` | Standing rebuttal and no standing support. |
| `contested` | Standing support and standing rebuttal. |

A claim with no evidence starts unresolved. Evaluation must report grounds and surviving objections, not a confidence score. These intended readings are **not a complete evaluation algorithm** and are not implemented by the storage schema.

### Open evaluator contract

The following decisions are unresolved and must be specified before application behavior can be considered complete:

- **Standing and propagation:** how source and observation status affect evidence grounded in an observation; how objections to evidence applicability affect that record; and how these dependencies interact.
- **Support for non-claim targets:** SQL permits `SUPPORTS` targeting sources, observations, and evidence. Its effect on standing, including whether any such target needs explicit support, has not been decided. An evaluator must not silently ignore these permitted records or invent an approved rule for them.
- **Cycles and status mapping:** choose an explicit evaluation procedure, including mutual rebuttals, self-reference, cycles through provenance, and cases whose standing cannot be resolved. Do not assume every cycle means `contested`, or that a named fixpoint procedure alone determines the public statuses.
- **Qualifications:** SQL restricts `QUALIFIES` to claims, but does not decide whether or how qualifications affect status, standing, or only explanatory output.
- **Counterfactual dependency handling:** define the consequences of hypothetically excluding a record for dependent observations and evidence, consistently with the standing rules.

Evaluation is intended to run at query time over the scoped ledger. No write operation updates a stored belief state. If caching is introduced later, it must remain an internal evaluator concern, not a new ledger field. The noncyclic example in §10 illustrates intended propagation, not a substitute for the missing rules.

## 4. Verdict Shape

`evaluate` returns one verdict object, never a score or a paginated collection:

```json
{
  "claim_id": "…",
  "claim_text": "…",
  "status": "believed",
  "support": { "chains": 1, "distinct_sources": 1 },
  "grounds": [
    { "evidence_id": "…", "reason": "…", "from_observation_id": "observation_291", "from_source": "Reuters" }
  ],
  "surviving_objections": [],
  "collapse_conditions": [
    { "retract": "observation_291", "flips_to": "unresolved" }
  ],
  "computed_at": "2026-10-04T13:20:00Z",
  "as_of": "2026-10-04T13:20:00Z"
}
```

- `support.chains` counts **standing supporting evidence records** for the claim. It does not enumerate paths or count documents.
- `support.distinct_sources` counts distinct `observations.source_id` values reached through those records' `from_observation_id` values. Several supporting records from one observation or one source can increase `chains` without increasing `distinct_sources`.
- Distinct source IDs do **not** establish independent reporting or rule out syndication. Neither count is confidence, resilience, or a guarantee of corroboration.
- `collapse_conditions` is intended to report **single-retraction status flips**: hypothetically exclude one record, re-evaluate, and report a changed status. It does not mutate the ledger. Minimal cut sets are outside v1; exact dependency handling awaits §3.
- `computed_at` is response metadata. `as_of` is the ledger cutoff used for the query, not an additional stored clock.

## 5. Identity and Retrieval Without Entities

**There are no entity nodes or identity-resolution links.** “The ‘Sam’ in this tweet is Sam Altman” can be a claim, supported or rebutted by evidence like any other. The evaluator does not parse that text, merge records, redirect references, or change retrieval because it contains an identity statement. Agents interpret it.

An agent can search for an existing claim and decide to use its ID or append another claim. Identical claim text is allowed and does not automatically connect or consolidate records. There is no hidden replacement mechanism.

**Retrieval is semantic.** “All claims about X” means embedding similarity over claim records, not an exact-match join on entity keys. Results are plausible matches, not guaranteed exhaustive coverage. An empty result is not proof that the ledger contains no relevant statements. Observation embeddings also support document retrieval; hashes can be looked up without implying deduplication.

**Classifications remain statements.** “Reuters is a news wire” is opaque claim text, not a typed `source_type` field. Any classification or entity projection belongs outside the base ledger.

### Embedding contract and unresolved index issue

- The selected model is **`Qwen/Qwen3-Embedding-8B`**, using its full **4096-dimensional** output with L2 normalization. No dimension reduction is planned here.
- Embeddings exist only on observations and claims. When present, the accompanying `embedding_model` identifies the model; the SQL pairing check does not itself enforce a particular model identifier.
- Retrieval queries use the selected model's query instruction; documents are embedded without that query instruction. Similarity is a retrieval mechanism, not a confidence input to evaluation.
- `vector(4096)` stores the full embedding. However, the SQL declares HNSW indexes using `embedding::halfvec(4096)`, while its documented pgvector limit for halfvec indexing is **4000 dimensions** (and 2000 for vector indexing).

**4096 exceeds 4000. The declared indexes are incompatible with that limit.** Casting to half precision does not reduce dimensionality and does not solve the issue. Indexed retrieval and successful schema initialization must not be claimed until this implementation issue is resolved. This document does not choose a workaround or change the model or SQL.

## 6. Time and Append-Only History

One stored clock: **`asserted_at`**, on all four tables, supplied by the database via `DEFAULT now()`. The API does not take agent-supplied assertion timestamps. The SQL default is a default, not a constraint prohibiting direct SQL writers from specifying a timestamp.

Everything else temporal stays in text:

- **Claim time is claim content.** “Layoffs happened in September 2026” stays inside the statement. Event-time extraction is an optional projection.
- **WHEN vs WHAT.** The ledger does not separately structure when something was supposedly true. An agent includes the relevant timeframe in its claim text.
- **Temporal interpretation belongs to agents.** If a document shows that evidence concerns a different timeframe, an agent may append evidence explaining that applicability objection. A naked assertion or new claim does not automatically alter another claim's status.
- **`as_of` scopes ledger membership.** Evaluation considers only records asserted at or before the cutoff, across all four tables and their relationships. It describes belief from information recorded by then, not the event time described in text.
- **Corrections are new records.** Append a new observation or claim and, where appropriate, grounded evidence explaining the correction. No automatic document-version linkage or retirement of earlier records exists.
- **No timer-based decay.** A time-sensitive claim does not lose status merely because time passes. Relevant changes must be represented through evidence and the evaluator's rules.

The SQL defines mutation-denial triggers for the four tables to reject `UPDATE`, `DELETE`, and `TRUNCATE`. It also contains stale comments and trailing trigger declarations referring to absent tables. Those declarations are an unresolved initialization issue, **not** additional supported tables or features. The four-table contract does not imply that the current initialization script runs successfully (§11).

Structural event-time queries, retroactive temporal models, prediction-versus-outcome logic, and mechanized temporal consistency checks remain outside v1.

## 7. MCP Surface (v1)

The server is **mechanical; the agent is interpretive**. Storage, retrieval, traversal, and counting belong in tools. Judgments about whether a text expresses a claim, whether two statements refer to the same thing, and why an observation matters belong to the agent.

**Exactly four write tools:** `add_source`, `add_observation`, `add_claim`, and `add_evidence`. Each appends a record; `add_evidence` requires a reason and a grounding observation. Writes do not accept agent-supplied `asserted_at` values and do not promise deduplication by content hash or claim text.

**Collection queries** return pagination envelopes with `total_count`, `page`, `page_size`, and `items`, plus a `summary` block with per-status counts where applicable. Counts precede content so an agent can explore cheaply. **Singleton reads, claim summaries, and verdicts return objects**, not pagination envelopes. Embedded arrays within a verdict remain part of that object.

| Tool | Purpose and response |
|---|---|
| `search_claims(text?, similar_to?, status?, as_of?, min_chains?, page?)` | Front door for semantic retrieval and world-state queries. Returns a collection envelope with per-status summary counts, then concise claim results with supporting/rebutting counts, not full evidence or reasons. Topic matches are believed-first; without `text` or `similar_to`, query the whole world state, most recent first. `min_chains` filters the standing-support record count, not confidence. |
| `get_evidence(target_id, relation?, depth?, page?)` | Collection of evidence bearing on a target. One hop by default; `depth` lets the agent request further traversal. |
| `get_claim_summary(claim_id)` | One metadata object: status, supporting/rebutting/qualifying counts (total and standing), `chains`, and `distinct_sources`; no reasons or full grounds. |
| `get_observation(id)` / `get_source(id)` | One full record object. Search results do not carry document payloads; observation content may be null. |
| `evaluate(claim_id, as_of?)` | One §4 verdict object with grounds, surviving objections, and collapse conditions. |
| `what_if_retracted(node_id)` | One object containing the hypothetical `retracted` ID and a `flips` array of status changes. No stored record is deleted. Dependency handling requires the §3 contract. |
| `diff(query?, as_of_a, as_of_b)` | Collection of status deltas between ledger cutoffs, with the evidence responsible for each change. |

Status-dependent filters, counts, and results require the same agreed evaluator rules; the schema alone cannot produce them.

**Deliberately absent:** tools that interpret text. There is no intake pipeline or automatic registration. The agent follows a recipe: search → interpret matches → reuse an ID or append a claim → add grounded evidence → request evaluation. Recipes live in prose, not hidden server semantics.

## 8. Layering: The Stack

Each layer reads what is below it. Outputs written back to the ledger use the four append tools, as claims with grounding observations and evidence rather than new score fields or relation types.

- **L0 — Ledger.** PostgreSQL records, append-only, with a fixed structure and opaque content.
- **L1 — Evaluator.** Intended query-time statuses and verdicts over L0 relationships. Writes no derived state. Its unresolved rules are listed in §3.
- **L2 — Optional projections, outside the current build.** A triple store may parse claims; an entity view may interpret identity statements; a numeric model may derive out-of-band scores. These do not change base-layer semantics.

A projection's numerical output can be quoted in a claim such as “Layer X rates this belief 0.72,” with evidence explaining its origin. That is a statement available for support or rebuttal, not a numeric input to L1. Projections cannot infer verified source independence from distinct source IDs.

## 9. V1 Scope

**In:** the four-table append-only storage model, the four append tools, semantic retrieval using the full selected embeddings, and the read surface described above. Query-time evaluation is intended v1 work, but its unresolved rules and the SQL initialization issues are prerequisites, not completed behavior.

**Out:**

- Typed entities, alias tables, and automatic identity resolution.
- Document-dependence and version-link mechanisms.
- Multiple belief contexts; v1 has one implicit context.
- Minimal cut sets for collapse conditions.
- Temporal decay and typed event-time filtering.
- Automatic text interpretation or semantic validation; v1 trusts the writing agent's judgments.
- Evaluation caching and status materialization in the ledger.
- Optional L2 packages and the separate Hermes client-integration package.

## 10. Worked Example

An agent records a Reuters article (`o1`), a skeptical blog post (`o2`), and a document analysis (`o3`), each linked to its source:

```text
claim c1: "Tesseralia laid off 15% of staff in September 2026"

evidence e1: o1 SUPPORTS c1 (reason: "Reuters cites the internal memo dated 2026-09-20")
evidence e2: o1 SUPPORTS c1 (reason: "Two employees confirmed on the record")
evidence e3: o2 REBUTS c1   (reason: "Blog claims memo is fake, citing metadata anomalies")
evidence e4: o3 REBUTS o2   (reason: "The document analysis authenticates the memo and explains why those metadata anomalies do not establish forgery")
```

**Intended noncyclic behavior:** `e4` stands, its rebuttal makes the blog observation `o2` unusable as grounds, and therefore `e3` does not stand. With `e1` and `e2` remaining standing support, `c1` is believed. This illustrates the same intended observation-to-evidence propagation as EXAMPLES.md, not an implemented SQL evaluation rule.

The resulting support counts would be `chains: 2` and `distinct_sources: 1`: both supporting records originate from the same observation and therefore the same source ID. They are not two independent reports. Hypothetically excluding `o1` would remove that support and leave the claim unresolved under this intended example. Adding a surviving rebuttal would instead make the claim contested. General propagation, cycles, and counterfactual dependencies still require the decisions in §3.

## 11. Implementation Stack and Outstanding Issues

- **Database:** PostgreSQL with pgvector. The SQL specifies PostgreSQL 16+ and pgvector 0.7+ and suggests a local Docker image such as `pgvector/pgvector:pg18`. Relational foreign keys express provenance and evidence targets; there is no separate graph database.
- **Embeddings:** full `Qwen/Qwen3-Embedding-8B`, 4096 dimensions, stored with paired nullable model metadata on claims and observations.
- **Server:** MCP append and read tools. Interpretation stays with the agent; evidence requires a nonblank reason, not every foreign key.
- **Open implementation issues:** the 4096-dimensional HNSW declarations exceed the documented 4000-dimensional halfvec index limit, and stale trigger declarations reference tables that are not defined. Do not describe the existing initialization script or indexed retrieval as working; SQL changes are outside this documentation update.
- **Open evaluation decisions:** standing and provenance propagation, support for non-claim targets, cycle handling and status mapping, qualification effects, and counterfactual dependency handling (§3).

These issues do not authorize additional tables, dimension reduction, identity-link features, or invented evaluation semantics. They identify the work needed to implement the stated design faithfully.
